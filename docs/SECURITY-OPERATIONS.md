# 보안·동시 사용·저장소 운영

외부 HTTPS / 내부 HTTP 구성을 유지한다. 이 문서는 소스 구현과 운영 적용 절차를 설명한다. 코드 수정만으로 실행 중인 Docker 이미지나 계정 파일은 변경되지 않는다.

## 인증과 클라이언트 식별

- 기본 앱 생성에는 `WebAuth`가 필수다. `allow_unauthenticated=True`는 카메라를 모의 객체로 대체한 테스트에서만 사용한다.
- 직접 접속은 TCP peer 주소를 사용한다. `ICSEE_TRUSTED_PROXIES`에 등록된 peer에 대해서만 `X-Forwarded-For`를 오른쪽부터 검사하여 첫 비신뢰 hop을 클라이언트로 선택한다.
- 기본 신뢰 프록시 목록은 비어 있다. 실제 프록시의 **백엔드 연결 주소**를 확인한 후 개별 IP 또는 최소 CIDR을 등록한다. `0.0.0.0/0`, `::/0`은 허용하지 않는다.
- 프록시는 외부에서 받은 전달 헤더를 덮어쓰거나 검증된 체인으로 추가해야 한다. NAT 게이트웨이를 등록한다고 원래 클라이언트를 식별할 수 있는 것은 아니다. 직접 LAN 접속과 프록시 요청이 동일한 peer로 보이면 신뢰 가능한 프록시 연결 경로를 먼저 분리해야 한다.
- HTTPS 공개 호스트에서는 Secure / HttpOnly / SameSite=Strict 쿠키를 유지한다. 내부 HTTP 정책은 변경하지 않는다.

요청 제한은 60초 이동 구간 기준이다. 값은 환경 변수로 조정한다.

| 구분 | 기본값 | 환경 변수 |
| --- | ---: | --- |
| 로그인 / IP | 20 | `ICSEE_LOGIN_IP_LIMIT` |
| 로그인 / IP+계정 | 10 | `ICSEE_LOGIN_ACCOUNT_IP_LIMIT` |
| 조회 / 사용자 | 240 | `ICSEE_READ_LIMIT` |
| 조회 / 세션 | 120 | `ICSEE_READ_SESSION_LIMIT` |
| 제어 / 사용자 | 60 | `ICSEE_CONTROL_LIMIT` |
| 제어 / 세션 | 30 | `ICSEE_CONTROL_SESSION_LIMIT` |
| 작업 요청 / 사용자·세션 각각 | 10 | `ICSEE_JOB_LIMIT`, `ICSEE_JOB_SESSION_LIMIT` |
| 스트림 연결 / 사용자 | 30 | `ICSEE_CONNECT_LIMIT` |
| 스트림 연결 / 세션 | 15 | `ICSEE_CONNECT_SESSION_LIMIT` |

계정 이름만으로 모든 IP의 로그인을 잠그지 않는다. 비밀번호 검증은 동시에 4개까지 실행하며 과부하 시 503을 반환한다. STOP·로그아웃은 일반 횟수 제한에서 제외하되 인증·권한·출처 검사를 유지한다. 잘못된 로그인 요청도 IP 예산에는 포함된다.

## 세션과 연결

세션은 8시간, 최대 128개다. 로그아웃·세션 교체·만료·계정 권한 변경·비활성화 시 활성 HTTP/영상/음성 연결을 취소한다. 만료 타이머는 브라우저의 다음 요청을 기다리지 않는다. 설정 변경은 파일 변경 감지 주기(최대 약 1초)에 반영한다.

서버는 폐기된 세션으로 추가 데이터를 보내지 않는다. 이미 브라우저에 수신된 프레임이나 다운로드된 파일을 회수할 수는 없다. 취소 후 카메라의 진행 중인 읽기와 FFmpeg 정리는 기존 소켓 timeout 범위에서 끝난다. 로그아웃 시 해당 세션의 다른 탭도 종료되며, 별도로 로그인한 다른 세션은 유지된다.

웹 서버는 같은 실행 디렉터리에서 하나만 시작할 수 있다. 다중 Uvicorn worker나 수평 복제는 지원하지 않는다. 이 제한으로 시청 인원과 세션 상태가 프로세스마다 따로 계산되는 것을 방지한다.

## 시청 및 변환 제한

- 동시 서버 미디어 전송은 최대 **3세션**이다. 로그인만 한 세션은 포함하지 않는다.
- 동일 세션에서는 영상 1개·듣기 1개를 함께 사용할 수 있다. 중복 탭의 같은 종류 연결은 거부한다. 사진 저장용 스냅샷 1개는 기존 시청 슬롯을 공유한다.
- 실시간 영상 변환은 1개, 듣기 수신도 1개를 공유한다. 각 시청자의 버퍼는 완성된 프레임/PCM 블록 2개로 제한한다. 느린 시청자에게는 오래된 데이터를 버린다.
- 영상 인코딩·변환은 **실시간 1개 + 저장 영상 2개 = 최대 3개**다. 실시간 자리는 미리 확보하므로 저장 영상 작업이 시청을 막지 않는다. 듣기용 오디오 변환 프로세스 1개는 별도다.
- PTZ와 말하기는 기존 단일 실행·시간 제한을 유지한다.
- 웹·촬영기·CLI는 같은 `ICSEE_RUNTIME_DIR`의 파일 잠금으로 변환 한도를 공유한다. 각각 다른 디렉터리를 지정하면 이 한도를 공유하지 못한다.
- Compose는 컨테이너당 기본 CPU 2개·메모리 1GiB·PID 128개를 제한한다. `ICSEE_CPUS`, `ICSEE_MEMORY`로 조정한다.

## 작업 큐

`runtime/jobs.sqlite3`에 작업을 저장한다. 전체 미완료 작업은 최대 32개, 사용자별 최대 3개다. 실행 작업자는 웹·촬영기 합계 최대 2개이며 OS 파일 잠금으로 조정한다.

- 타임랩스 생성: POST 응답은 `202`와 `job_id`, `status_url`이다. UI는 대기/실행/완료/실패를 표시하고 취소를 지원한다. 임의의 진행률 백분율을 표시하지 않는다.
- SD 미리보기: 서버가 확인한 녹화 항목만 큐에 넣고 기존 요청은 결과를 기다린다. 요청 취소·로그아웃·연결 끊김 시 해당 작업을 취소한다.
- 작업 조회·취소는 소유자 또는 관리자에게만 허용한다.
- 동일한 활성 작업은 중복 실행하지 않는다. 다른 사용자의 동일 작업 ID는 노출하지 않는다.
- 대기 작업은 재시작 후 유지한다. 정상 종료 시 실행 작업은 취소한다. 강제 종료로 중단된 실행 작업은 실패로 표시하고 자동 재실행하지 않는다. 사용자는 상태 확인 후 재요청할 수 있다.
- 완료·실패·취소 기록은 새 작업 등록 시 30일 기준으로 정리한다.
- 로그아웃 후에도 이미 접수된 타임랩스 생성은 계속된다. 작업 취소 버튼으로 별도 취소한다. SD 요청은 연결 수명과 함께 취소한다.

## 계정과 역할

| 기능 | viewer | operator | admin |
| --- | :---: | :---: | :---: |
| 영상·듣기·기존 보관 영상 조회 | O | O | O |
| 장치 연결 확인·SD 목록 조회 | O | O | O |
| PTZ·말하기·추적 설정 | - | O | O |
| 타임랩스 생성·SD 구간 가져오기 | - | O | O |
| 운영 상태·보관 정책 | - | - | O |
| 프리셋 목록·저장·덮어쓰기·이동·삭제 | - | - | O |

화면 표시와 별도로 HTTP API·WebSocket에서 권한을 검사한다. 기존 단일 계정은 관리자로 읽는다. 신규 계정 파일은 `version: 2`, PBKDF2-SHA256(600,000회) 검증용 해시를 사용한다. 계정 관리 CLI는 로컬 파일 권한을 가진 운영자가 실행하며 웹 계정의 비밀번호를 명령 인자로 받지 않는다.

프리셋은 모두 `/api/admin/presets` 아래에 있으며 기본 조회도 admin 전용이다. 목록은 사용자가 새로고침할 때만 카메라에서 읽는다. 저장·덮어쓰기·삭제는 카메라 목록을 재조회해서 결과를 확인하며, 통신 실패 시 결과를 미확인으로 표시하고 자동 재시도하지 않는다. 사용자 이름·기존 역할은 이번 프리셋 권한 정책 때문에 변경하지 않는다.

프리셋 변경과 수동 PTZ 이동·자동 추적 설정 변경은 웹 프로세스의 공통 제어 잠금을 사용한다. 자동 추적이 켜져 있으면 프리셋 변경을 거부하며 자동으로 추적을 끄지 않는다. 실제 카메라의 장비·펌웨어와 검증 기록을 비교한다. 외부 제조사 앱이나 별도 CLI의 동시 제어까지 이 잠금이 차단하지는 않는다.

위치 이동은 검증 프로필에 물리 검수 기록이 있을 때만 UI와 서버 양쪽에서 허용한다. ONVIF의 프리셋 개수 광고나 GotoPreset 응답만으로 이동 성공을 인정하지 않는다. 검수 후 이동을 허용하더라도 최대 2초의 독립 STOP watchdog, 최종 STOP, 로그아웃·만료·HTTP 연결 종료 취소를 적용하며 응답은 도달 성공을 단정하지 않는다. 홈 위치·자동 순회는 제공하지 않는다. 장치가 STOP을 실제로 수행하는지와 2초 안에 도달 가능한 이동 범위는 별도 영상·사용자 관찰 검수가 필요하다.

2026-10-26 확대 시험에서 현재 펌웨어가 ONVIF Stop에 응답하고도 GotoPreset 이동을 계속하는 것을 확인했다. 프리셋 정지는 DVRIP STOP을 먼저 보내고 ONVIF Stop도 시도하도록 보완했으며, 주 연결과 watchdog 연결은 독립이다. 이동 허용 기록은 `preset_protocol=onvif`, `preset_stop_protocol=dvrip`, `preset_motion_and_stop=confirmed_by_user`를 모두 요구한다. 이후 사용자가 목표 위치 정지·중간 정지 유지·원위치 복귀 정지를 모두 확인해 세 플래그를 설정하고 admin 이동을 활성화했다. 검증 범위는 가까운 수평 위치이며, 먼 위치·수직 전체 범위·홈·순회는 포함하지 않는다.

```sh
# 기존 계정의 ID/비밀번호를 유지하며 파일을 해시 형식으로 이관
.venv/bin/python -m icsee_ptz accounts migrate
# ID·역할·활성 여부만 조회
.venv/bin/python -m icsee_ptz accounts list
# 신규 조회자 생성: 비밀번호는 숨김 프롬프트에서 입력
.venv/bin/python -m icsee_ptz accounts set --username viewer1 --role viewer
# 기존 계정의 역할 변경 (비밀번호 유지)
.venv/bin/python -m icsee_ptz accounts set --username viewer1 --role operator
# 비밀번호 재설정
.venv/bin/python -m icsee_ptz accounts set --username viewer1 --role operator --reset-password
.venv/bin/python -m icsee_ptz accounts disable --username viewer1
```

`--auth-config`로 다른 파일을 선택할 수 있다. 마지막 활성 관리자는 비활성화하거나 강등할 수 없다. 파일 쓰기는 원자적으로 교체하며 기존 파일 권한을 유지한다. 비밀번호·해시·세션 토큰은 CLI 결과와 운영 로그에 출력하지 않는다.

**현재 Compose는 계정 파일을 개별 bind mount한다.** 호스트에서 원자적으로 교체한 파일의 새 inode를 컨테이너가 보도록 계정 변경 후 `docker compose up -d --force-recreate web`이 필요하다. 단순 restart로 충분하다고 가정하지 않는다. 호스트 직접 실행 또는 적절한 권한의 디렉터리 mount 환경에서는 파일 변경을 자동 감지한다.

## 저장소

일별 컷 수·JPEG 용량·첫/마지막 촬영 시각과 전체 등록 용량을 DB 트리거로 갱신한다. 일반 상태 조회와 촬영 중 용량 검사는 전체 파일을 순회하지 않는다. 인코딩 중 출력 경로를 DB에 등록하여 임시 출력 크기와 DB 파일 크기도 용량 계산에 포함한다. 변환 중 디스크 여유·촬영기에서 설정한 저장 한도를 점검하며 기준을 넘으면 임시 출력을 폐기하고 원본을 보존한다. 파일시스템의 강제 quota를 설정하는 기능은 아니다.

날짜별 생성·보관 정리는 작업 큐에서 수행하므로 촬영 루프를 인코딩으로 막지 않는다. 작업 큐가 가득 차도 촬영을 계속하며 다음 촬영 주기에 유지보수 등록을 다시 시도한다. 보관 기간은 기본 사진 3일·영상 30일이며 관리자 설정 화면에서 1~365일로 변경한다. 영상 보관 기간은 사진 이상이어야 한다. 변경된 기간은 다음 보관 정리에 적용된다.

```sh
# 실제 파일과 DB 대조, 집계 재구축. 파일을 삭제하지 않음
.venv/bin/python -m icsee_ptz timelapse reconcile
# 촬영 중지 상태에서만: 표준 이름·날짜·JPEG 형식의 미등록 사진을 복원
.venv/bin/python -m icsee_ptz timelapse recover
```

누락·변조 파일은 임의로 정상 판정하지 않는다. 알 수 없는 파일과 미등록 MP4는 보존하고 진단 결과에 표시한다. 복구는 한 번에 보고된 최대 100개 후보를 대상으로 하므로 결과를 확인한다.

## 경로와 적용 순서

- `ICSEE_PROJECT_DIR`: 프로젝트 기준 경로, 기본 현재 작업 디렉터리
- `ICSEE_DATA_DIR`: 데이터 경로, 기본 프로젝트의 `data`
- `ICSEE_RUNTIME_DIR`: 공유 잠금·작업 DB, 기본 데이터의 `runtime`
- `ICSEE_CONFIG_DIR`: 계정 파일 디렉터리, 기본 프로젝트의 `config`
- `ICSEE_CAMERA_PROFILE`: 검증 프로필 파일, 기본 프로젝트의 `camera-profile.json`

적용 순서:

1. 테스트를 실행하고 운영 계정·DB를 접근 권한이 제한된 위치에 백업한다. 실행 중 SQLite는 일관된 DB 백업 방식을 사용한다.
2. 실제 외부 프록시 경로와 peer IP를 확인하고 신뢰 프록시를 최소 범위로 설정한다.
3. 선택적으로 계정 파일을 이관한다. 평문 호환 읽기는 지원하지만 새 계정 관리 CLI는 해시 형식으로 저장한다.
4. 웹·촬영기를 함께 새 이미지로 재생성한다. 기존 촬영 설정을 유지하고 실제 카메라 모터 시험은 별도로 수행한다.
5. 3세션 동시 시청·4번째 거부·로그아웃·만료·권한 거부·촬영 지속·작업 취소를 확인한다.

원복 시 새 큐 작업자를 모두 중지하고 미완료 작업 상태를 확인한다. 기존 `frames`/`exports` 테이블은 유지하므로 영상·사진을 다시 복사할 필요는 없다. 이전 앱은 새 해시 계정 형식을 읽지 못하므로 원복용 인증 설정은 별도로 준비해야 한다. 원복 후 다시 새 버전을 적용하면 `timelapse reconcile`로 파생 집계를 재구축한다.

## 검증 범위

테스트는 별도 데이터·실행 디렉터리를 사용한다. 실제 카메라·운영 계정에 로그인하지 않고 세션 취소, 역할, 프록시 식별, 다중 작업자 상한, 실제 FFmpeg 파일 변환, 저장소 복구를 검증한다. 보안 이벤트 로그에는 선택된 상태·종류·작업 ID만 기록하며 원격 응답 본문, 비밀번호, 세션 쿠키, FFmpeg 인자는 기록하지 않는다.
